# Phase 5 Review — Cutover Preparation & Parity Validation

Named `Phase5Review.md` rather than the generic `PhaseReview.md` the mission requested, matching the collision-avoidance precedent set in `Phase2Review.md`/`Phase3Review.md`/`Phase4Review.md`.

## Scope delivered

A systematic behavioral comparison of `server/local.js` against `server/src/` across all 15 areas the mission listed, producing 5 required artifacts (Parity Matrix, Behavior Matrix, API Compatibility Matrix, Database Compatibility Matrix, Migration Readiness Checklist — all in `docs/architecture/ParityValidation.md`), a documented, honest real-MariaDB-connection attempt, and a security review. **No production code was changed** — no `local.js` edits, no frontend edits, no new features, no cutover. This is purely a verification and documentation phase, exactly as scoped.

## What made this phase different from a rubber-stamp "looks fine" pass

1. **The real MariaDB connection attempt was pursued harder than in any prior phase, and still failed for the same reason.** Root requires a password this session doesn't have; the current OS user has no `auth_socket`-style passwordless access either; no credentials exist anywhere in the project's own config (`server/.env` only configures `local.js`'s SQLite-based app). Per this engagement's standing constraint, no bypass was attempted (no password reset, no `--skip-grant-tables`) — this machine also runs Jenkins and a separate PostgreSQL instance, clearly a shared, in-use development environment. This is documented as an honest, repeated gap (`ParityValidation.md` §6), not glossed over or faked.
2. **A genuinely new finding surfaced**: the Operations-domain routes added in Phase 4 have no rate-limiting middleware applied, unlike every auth-related route in both codebases. This wasn't caught during Phase 4 itself because Phase 4's own review focused on business-rule fidelity, not cross-cutting security conventions — Phase 5's explicit "verify... Rate Limiting" checklist item is what surfaced it. Classified as a **Bug** (an omission), not a documented decision, and deliberately left unfixed in this phase per its own "do not introduce new features" / validation-only scope — flagged clearly for a near-term follow-up instead.
3. **A stale documentation trail was found and named, not silently corrected**: `server/src/routes/licenses/README.md` refers to "Phase 4 (SaaS Licensing & Subscriptions)" — a leftover from an earlier, different phase-numbering scheme that predates the current Enterprise Constitution's Phase 1→5 sequence (this reconstruction's actual Phase 4 was Operations Domain Implementation). Left as-is rather than edited, since fixing stale planning docs wasn't in this phase's scope and touching them risked scope creep into unrelated cleanup.
4. **Re-verified rather than assumed a prior finding**: confirmed directly (not just cited from memory) that `local.js` does set `PRAGMA foreign_keys = ON`, and that `user_sessions`' `CREATE TABLE` statement genuinely declares no `REFERENCES` clause — closing a small gap in how confidently Phase 2's original "no FK" finding could be stated.

## Confidence level, honestly stated

High for everything comparable via direct code reading and the existing mocked test suites (611 total assertions across both stacks, all still passing, zero regressions from this phase since no source code changed). **Zero confidence, explicitly, for anything requiring a live database** — performance numbers, real transaction/rollback behavior, real constraint enforcement under concurrent load, and connection-pool behavior under real conditions are all unverified, exactly as every prior phase has honestly stated. This is not a new problem Phase 5 introduced; it's the same standing gap made more visible by a phase whose entire mission was to try to close it.

## Recommendation for the next phase

**Do not proceed to production cutover planning until a credentialed MariaDB instance is available and every currently-skipped integration assertion (Phase 2's `identityCore.integration.test.js`, Phase 4's `operationsCore.integration.test.js`, both `database.test.js` files) passes for real**, and real performance numbers are captured. Separately and independently of the database gap: fix the missing rate limiting on Operations-domain routes (small, well-scoped, doesn't require a live database to fix or test), and treat the JSON-blob-to-normalized-tables data migration and the entire unported Licensing/Administration/Cloud Backup domains as the major remaining bodies of work before any real cutover is achievable.
