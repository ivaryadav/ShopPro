# RC1 Sprint 3 Review — Cloud Backup Domain

Named `Sprint3Review.md`, matching the collision-avoidance precedent set by every `PhaseNReview.md`/`SprintNReview.md` since Phase 2.

## Scope delivered

Migrated ONLY the Cloud Backup domain from `server/local.js` into `server/src/`: Backup creation, restore, deletion (Part A — the `/api/cloud/*` HTTP domain), plus a new MariaDB-native operational backup/verify tool analogous to the pre-existing SQLite `backup-verify.js` (Part B). One new table (`cloud_backups`, migration 005), one new repository, one new service (Part A) plus one new service (Part B), one new controller, one new router mounting 3 endpoints, one new CLI script, 28 new test assertions (9 mocked + 11 real-database HTTP-domain integration + 8 real-database/real-`mysqldump` Part B integration), and full documentation. Explicitly did not touch Inventory, Sales, Repairs, Expenses, Authentication, Administration, Licensing, Frontend, Reporting, or Analytics — reused Sprint 2's `requireAdminSession` unmodified.

## What made this sprint different from Sprints 1 and 2

1. **A structurally different table.** Every domain migrated so far has been `tenant_id`-scoped. `cloud_backups` has no `tenant_id` column at all — it's keyed purely by a license-key hash from the offline desktop product (ADR-0003). Required a real architectural judgment call (documented in `Backup.md`) on whether this table belongs in the MariaDB migration at all, resolved by distinguishing "the desktop's own client-side data model" (out of scope, ADR-0003) from "server-side data the desktop calls into over HTTP" (in scope, ADR-0002).
2. **Two unrelated systems share the word "backup" in this codebase.** `cloud_backups`/`/api/cloud/*` (a per-license sync bridge) and `server/scripts/backup-verify.js` (a SQLite-file-level DevOps tool) are completely different concepts that happen to share a name. This sprint ported analogs of BOTH, and kept them clearly separated in code and docs to avoid the two being conflated.
3. **This sprint added a genuinely new capability (Part B) rather than only porting an existing one.** Parts of the mission ("Verify backup integrity," "Verify restore integrity," the DATA SAFETY section) have no direct `local.js` equivalent to port for the MariaDB engine specifically — `local.js`'s own backup tooling is SQLite-file-based and already exists unmodified. Part B is a deliberate, in-scope exception to "no new features": the mission itself requires backup/restore integrity verification for the database this engagement is migrating TO, and no such tool existed for MariaDB before this sprint.
4. **Real-database testing found a real, data-safety-relevant bug — in code THIS sprint wrote**, not in ported `local.js` behavior. `verifyBackup`'s initial implementation only checked tables that successfully landed in a restored scratch database; a truncated/corrupted dump that dropped several tables entirely still reported `ok: true`, because every table that DID restore passed its own individual check. Fixed by adding an explicit live-vs-restored table-set comparison, reproduced and regression-tested against a real, deliberately-truncated dump on a real disposable MariaDB instance. This is the sharpest confirmation yet, across all three sprints, of why this engagement insists on real-database testing over mocks: the bug was invisible to any test that didn't actually restore a genuinely broken dump into a genuinely separate database and inspect the real result.

## Confidence level, honestly stated

High for the entire scope this sprint's real-database integration tests exercised: create/restore/upsert-overwrite/delete (including the deliberate unconditional-delete quirk) against a real MariaDB instance, cross-key-hash isolation (the only isolation boundary this table has), corrupted/missing-backup handling, and — after the fix above — genuine corruption detection for Part B's dump/restore/verify cycle, including confirmed scratch-database cleanup on both success and failure paths. **Lower, and explicitly flagged, for gaps that are real but out of this sprint's stated scope**: no rate limiting on the 3 HTTP endpoints (a preserved `local.js` characteristic, not hardened here); no filesystem-based security surface exists to test (directory traversal, filename sanitization) because `local.js`'s real implementation has none.

## Recommendation for the next sprint

This closes the loop Sprint 2's own review flagged as the last real gap: "Cloud Backup (`/api/cloud/*`) and the offline-desktop license engine... remain entirely unported." Cloud Backup is now done. The one remaining unported piece across this entire engagement is `server/license.js`'s offline-desktop license-key engine (`/api/admin/generate-key`/`validate-key`) — explicitly out of scope for every sprint so far per ADR-0003, and not addressed here either. Per this sprint's explicit mission, Audit Logging and Release Candidate work do not begin until a future, separately-authorized sprint.
